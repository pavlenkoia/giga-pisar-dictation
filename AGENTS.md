# Giga Pisar Dictation — правила работы агентов

## Источники и документация

- `docs/initial-spec.md` — исходный черновик для проектирования, а не окончательное техническое решение. Прочитайте его перед первым планированием; рекомендации и открытые вопросы требуют согласования.
- Актуальные требования, принятые решения и инструкции храните в `docs/`. Точка входа — `docs/README.md`; существенные архитектурные решения — в `docs/decisions/`.
- При расхождении документов обозначьте конфликт и согласуйте изменение; не переопределяйте требования молча.
- Используем только `docs/`, без отдельной llm-wiki. По завершении задачи обновляйте затронутую документацию либо объясняйте, почему обновление не требуется.

## Планирование

- Основной агент исследует задачу и готовит план сам. Исследование и планирование автоматически не делегируются.
- Планы сохраняйте в `plans/YYYY-MM-DDTHH-mmZ-<название>.md` с временем UTC, не в корневом `PLAN.md`.
- В плане указывайте цель, границы, затрагиваемые пути, решения для согласования, шаги, критерии готовности, проверки и необходимость обновить `docs/`.
- Реализацию начинайте после одобрения плана в Plannotator и команды на исполнение. Если Plannotator недоступен, получите явное одобрение в чате.
- Небольшие правки документации и настроек по прямому запросу пользователя не требуют отдельного плана и запуска worker.

## Реализация и приёмка

- Основной агент координирует исполнение одобренного плана; код реализует встроенный `worker` со свежим контекстом.
- Модели ролей задаёт `.pi/settings.json`. Не подменяйте согласованные модели или способ исполнения молча; при недоступности сообщите блокер.
- Передайте worker план, необходимые документы, границы изменений, критерии готовности и проверки.
- Один пишущий агент на рабочее дерево; параллельных исполнителей изолируйте отдельными worktree.
- Основной агент независимо проверяет diff и фактические результаты проверок, затем запускает свежего read-only `reviewer` по плану, требованиям и diff.
- Отчёт исполнителя не равен приёмке. Подтверждённые замечания возвращайте на исправление и проверяйте повторно.
- Не смешивайте задачу с посторонним рефакторингом.

## Проверки

- Используйте реальные команды проверок проекта и документируйте их после выбора стека. Не заявляйте об успехе без фактического запуска.
- Автотесты по умолчанию должны работать без настоящего ключа, LAN-сервера, микрофона и изменений пользовательского clipboard; внешние эффекты заменяйте тестовыми адаптерами.
- Изменения desktop-интерфейса и вставки проверяйте отдельно в целевой графической сессии. Сборка, моки или браузерная проверка не заменяют проверку GTK/X11.
- В финальном отчёте укажите изменённые файлы, проверки и результаты, обновление документации, оставшиеся риски и непроверенные сценарии.

## Безопасность

- Не раскрывайте API-ключи в коде, репозитории, чате, журналах или аргументах процессов. Не журналируйте аудио и транскрипты по умолчанию.
- Не меняйте сервер, системные настройки, установку и автозапуск без отдельного разрешения.
- Запись микрофона, передачу реального аудио, изменения clipboard, фокуса и горячих клавиш выполняйте только в согласованном тестовом сценарии.

## Git

- Перед изменениями проверьте ветку и рабочее дерево; используйте ветку задачи `feature/…`, `fix/…` или `chore/…`, не `main`.
- Не перезаписывайте чужие изменения. При пересечении с задачей уточните порядок работы.
- Commit, push и merge выполняйте только по команде пользователя; не обходите настроенные ограничения репозитория.
